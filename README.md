# Стирка ON

![stirki](./stirki_bot_logo.jpg)

Гиперлокальный сервис доставки стирки в Мытищах: https://stirkaon.com.
Клиент находит сервис по QR-коду на листовке, оформляет заказ в PWA, пеший курьер
забирает бельё у двери, мы стираем, сушим, гладим и возвращаем.

Открытые задачи — в [`docs/TODO.md`](docs/TODO.md). Текст оферты — [`docs/оферта.txt`](docs/оферта.txt)
(на сайте показывается из `frontend/src/components/ui/OfferModal.tsx`, при правках менять оба).

## 1. Как сервис работает для клиента

```
QR на листовке → stirkaon.com → лендинг → /login (телефон + SMS) → /order (карточки)
    → корзина → заказ → [бесплатно: сразу в работу | платно: оплата в Точке]
    → /order/:id — статус заказа → доставлено
```

1. **QR-код.** Листовки ведут на главную без параметров, поэтому отличить переход с листовки (и с какого дома)
   от другого захода нельзя — считаются все заходы неавторизованных посетителей на главную. Заход пишется в
   `landing_visits` не чаще раза за сессию вкладки; браузер получает случайный `visitor_id` (localStorage),
   по нему считаются уникальные посетители. В админке «Посещения сайта» — по дням (МСК): всего заходов и уникальных.
2. **Вход.** Телефон и email → 4-значный код по SMS (SmsAero, TTL 5 мин, повтор не чаще раза в 58 с,
   5 неверных вводов сжигают код) → для новых клиентов имя. Токен живёт 60 дней и продлевается.
   Под телефоном две галочки (требование SMS-сервиса): «принимаю оферту и политику» — обязательна, без неё
   сервер не отправляет код; «согласен на рекламные СМС» — по желанию, изначально пустая. После подтверждения
   кода время согласий пишется в `clients.offer_accepted_at` / `sms_marketing_consent_at` (null — согласия нет);
   вход со снятой галочкой рассылки отзывает прежнее согласие. В админке — колонка «Согласие на рассылку».
   Email обязателен (на него Точка отправляет кассовый чек), сохраняется в `clients.email` после
   подтверждения кода, при каждом входе перезаписывается.
3. **Заказ** — вертикальные карточки:
   - **Адрес** — только выбор из списка (зона обслуживания в `src/addresses.py`), подъезд, этаж, квартира, комментарий. Адрес прошлого заказа подставляется.
   - **Тариф** — бесплатный или платный (см. ниже).
   - **Машинка** (только бесплатный тариф) — витрина: состояния случайные, реального парка за ней нет.
   - **Что стираем** — пакет или вещь, допуслуги, на бесплатном тарифе — просмотр рекламы (картинки, включённые в админке «Реклама», каждый показ пишется в `ad_views`).
4. **Оплата** (платный тариф). Заказ создаётся в статусе «Ожидает оплаты», клиент уходит на платёжную
   ссылку Точки (СБП, карта или T-Pay, ссылка живёт 1 час). Статус оплаты сервер сверяет с Точкой сам:
   при возврате клиента, при открытии заказа и фоновой задачей раз в минуту. Оплачен → «В пути»;
   отклонён или ссылка истекла → «Отменено».
   Ссылка создаётся методом `payments_with_receipt` — с кассовым чеком по 54-ФЗ, который Точка шлёт на
   email клиента. Позиции чека — пакеты и вещи (`PricingService.order_lines`): количество = число
   пакетов/вещей, цена за единицу уже включает допуслуги, они же перечислены в названии позиции.
   В конце названия — номер заказа («Стирка одной вещи (глажка), заказ ST-123»): названия позиций
   печатаются в чеке всегда, поэтому чек с почты клиента однозначно находится в админке.
   Без НДС (`vatType: none`), предмет расчёта — услуга, полный расчёт. Бесплатные заказы чека не имеют.
   Документация API Точки — локально в `docs/tochka/` (в git не хранится: 2,8 МБ, и GitHub принимает ссылки на
   публичные ключи Точки в ней за секреты). Скачать: https://developers.tochka.com/llms-full.txt,
   https://developers.tochka.com/llms.txt, https://enter.tochka.com/doc/openapi/swagger.json.
   `swagger.json` главнее текста `llms-full.txt`.

   **Номера заказа и платежа.** Номер заказа — `ST-<orders.id>` (`Order.number`), одинаковый на сайте,
   в письмах операторам и в админке. У платежа в Точке три идентификатора, все хранятся в `orders`:
   - `payment_link_id` — `paymentLinkId`, номер заказа для Точки: `ST-123-K7Q2`. Его видит клиент на
     странице оплаты, по нему оператор ищет заказ в админке (поиск в «Заказах») по реестру Точки.
     Случайный хвост нужен, потому что Точка не принимает повторный `paymentLinkId`, а `orders.id`
     повторяется: локальная разработка ходит в ту же Точку, а БД пересоздаётся с нумерацией с 1.
   - `operation_id` — ID операции, его выдаёт Точка; по нему сервер сверяет статус оплаты.
   - `payment_token` — секретный UUID в адресе возврата после оплаты (`/?payment_token=…`), клиенту
     как номер не показывается.
5. **Статус заказа** — таймлайн, поллинг раз в 60 с, контакты поддержки.
6. **Операторы** получают письмо о каждом новом заказе (бесплатный — сразу, платный — после оплаты)
   и двигают статусы вручную в админке `/admin`.

### Тарифы и правила

| | Бесплатный | Платный |
|---|---|---|
| Цена | 0 ₽ | по прайсу из БД |
| Условие | просмотр рекламы | оплата через Точка Банк |
| Что стираем | только пакет до 3 кг | пакеты и вещи |
| Лимит позиций | 1 пакет | 5 пакетов + 1 вещь |
| Допуслуги | нет | глажка, кондиционер, вакуумный пакет |
| Ограничение | 1 бесплатный заказ в сутки (МСК) на адрес | — |

- **Цена** = (база + допуслуги за пакет) × пакеты + (цена вещи + допуслуги за вещь) × вещи.
  Допуслуги выбираются на весь заказ и применяются к каждой позиции. Прайс — таблица `services`, цены — как в оферте
  (пакет 990 ₽, вещь 190 ₽, глажка +190 ₽ за вещь / +990 ₽ за пакет, кондиционер +100 ₽, вакуумный пакет +150 ₽).
  Если у допуслуги цена за пакет другая, она задаётся отдельной услугой со slug `<допуслуга>_bag` (сейчас только
  `ironing_bag` — «Глажка пакета»); такая услуга не выбирается сама и не показывается клиенту отдельной строкой.
- **Приём заказов** — ежедневно 9:00–22:00 МСК (курьеры работают 8:00–23:00). Вне часов сервер отклоняет заказ, клиенту показывается модалка.
- **Один активный заказ** на клиента. Неоплаченный заказ не считается активным.
- Лимиты, часы приёма, лимит бесплатных заказов на адрес, число и длительность рекламы, доступность бесплатного тарифа — меняются в админке («Системные настройки»), без деплоя.

### Статусы заказа

`waiting_payment` (Ожидает оплаты) → `courier_pickup` (В пути) → `picked_up` (Забрали) → `washing` (Чистим)
→ `courier_delivery` (Идём отдавать) → `delivered` (Доставлено); в любой момент — `canceled` (Отменено).
Каждая смена пишется в `order_status_history` с отметкой, кто изменил (`system`, `admin`, `tochka`).

## 2. Устройство проекта

```
src/          бэкенд: FastAPI, async SQLAlchemy, sqladmin
frontend/     PWA: React 19 + TypeScript + Vite + vite-plugin-pwa
pg_init/      SQL-схема БД и сид-данные (единственный источник правды по таблицам)
advertising/  файлы рекламных картинок (раздаются бэкендом как /advertising/*; в Docker — том)
restyle/      HTML-макеты дизайна (референс, в сборку не входят)
http_requests/ запросы для HTTP-клиента IDE (SmsAero, Точка)
```

### Бэкенд

Слои, зависимости только вниз:

```
src/api/routers/   эндпоинты, валидация, HTTP-ошибки
src/services/      бизнес-логика и интеграции
src/repositories/  запросы к БД, коммиты
src/models/        ORM-модели
```

- `src/schemas/` — Pydantic-модели запросов/ответов, `src/enums.py` — статусы заказа и оплаты, `src/settings.py` — настройки из `.env` (по классу на подсистему).
- Сервисы: `pricing.py` (цена), `payment.py` (Точка Банк), `payment_sync.py` (сверка оплат + фоновая задача), `notifications.py` (email операторам), `schedule.py` (часы приёма, МСК), `sms.py` (SmsAero), `auth.py` (генерация кода).
- Авторизация: Bearer-токен (UUID в `clients.auth_token`), зависимость `get_current_client` в `src/api/dependencies.py`.
- Создание заказа сериализуется `pg_advisory_xact_lock(client_id)`, чтобы не получить два активных заказа.
- Некритичная интеграция (email операторам) не роняет основной сценарий: ошибки только логируются.
- Админка — `src/admin.py` (sqladmin), вход по `ADMIN_USERNAME` / `ADMIN_PASSWORD`.

### Фронтенд

Только React + react-router: без state-менеджера и UI-кита.

- Страницы в `frontend/src/pages/`: `LandingPage` (`/`), `LoginPage` (`/login`), `OrderPage` (`/order`), `OrderStatusPage` (`/order/:id`).
- `OrderPage` владеет всем состоянием, карточки (`components/swipe/`) — презентационные.
- API — только через `api/client.ts` (fetch, Bearer, таймаут 15 с) и `api/index.ts`. Типы зеркалят схемы бэкенда — `types/index.ts`.
- Стили — один `index.css`, иконки — Font Awesome.

### База данных

PostgreSQL 16. Схема и начальные данные (статусы, прайс, настройки) — `pg_init/01-schema.sql`,
единственный источник правды. Файл выполняется **только при первом создании тома** Postgres. Миграций нет:
реальных клиентов пока нет, поэтому после правки `01-schema.sql` БД пересоздаётся. Все данные (клиенты, заказы,
правки в админке) при этом удаляются.

```bash
docker compose --profile prod down        # остановить контейнеры (тома остаются)
docker volume rm stirki_pg_data           # удалить БД
./run.sh local                            # или ./run.sh dev / prod на сервере — БД создастся из pg_init
```

> Когда появятся реальные клиенты, пересоздавать БД будет нельзя — тогда понадобятся миграции.

Основные таблицы: `clients`, `orders`, `order_statuses`, `order_status_history`, `services`,
`system_settings` (одна строка с рантайм-настройками), `landing_visits` (+ представление `landing_visit_stats`), `ad_views`.

### Соглашения

- Язык проекта — русский: тексты для пользователя, комментарии, коммиты, документация. Имена в коде и slug'и — английские.
- Статусы, услуги и улицы между слоями передаются латинскими slug'ами, кириллица — только для отображения.
- Комментарии объясняют «почему», а не «что».
- Линтер: `uv run ruff check src/`.

## 3. Запуск

### Переменные окружения

```bash
cp .env.example .env
```

| Переменные | Зачем |
|---|---|
| `DB_USER`, `DB_PASSWORD`, `DB_PORT` | PostgreSQL |
| `DOMAIN` | домен для Caddy (HTTPS), CORS и адреса возврата после оплаты |
| `APP_ENV` | `development` — SMS не отправляется, **код возвращается прямо в ответе API**; `production` — реальные SMS |
| `SECRET_KEY`, `ADMIN_USERNAME`, `ADMIN_PASSWORD` | сессии и вход в админку; в `production` без своих `SECRET_KEY` и `ADMIN_PASSWORD` бэкенд не запускается |
| `SMSAERO_EMAIL`, `SMSAERO_API_KEY` | SMS с кодом входа |
| `TOCHKA_TOKEN`, `TOCHKA_CUSTOMER_CODE_BUISNESS` | эквайринг Точка Банк |
| `TOCHKA_TAX_SYSTEM_CODE` | необязательно: система налогообложения для чека (`usn_income`, `patent`, …); пусто — не передаётся |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `NOTIFY_EMAIL` | письма операторам о новых заказах (для mail.ru нужен «пароль для внешних приложений»); `NOTIFY_EMAIL` — один или несколько адресов через запятую. Названия допуслуг в письме — из таблицы `services`, у платного заказа есть «Платёж в Точке» (`payment_link_id`). Не настроено — письма не отправляются, в логе предупреждение |

> ⚠️ `APP_ENV=development` нельзя оставлять на сервере, открытом для людей: кто угодно сможет
> войти под любым номером телефона. Оплата в dev-режиме **не** отключается — платный заказ
> создаёт реальную ссылку в Точке.

### Режимы `run.sh`

| Команда | Что запускается |
|---|---|
| `./run.sh local` | Postgres и Adminer в Docker; бэкенд (uvicorn `--reload`, :8001) и фронтенд (Vite, http://localhost:5173) на хосте. `APP_ENV=development` |
| `./run.sh dev` | весь стек в Docker (бэкенд, сборка фронтенда, Caddy), `APP_ENV=development` |
| `./run.sh prod` | весь стек в Docker, `APP_ENV=production` |
| `./run.sh stop` | остановить всё |

Локально: код входа показывается прямо под полем ввода. Админка — http://localhost:5173/admin,
Adminer — http://localhost:8081.

### Сервер

Рабочий сервер: FirstVDS, Ubuntu 24.04, `ssh stirki` (root), проект в `/opt/stirki`, домен
stirkaon.com → 195.140.146.185 (DNS у FirstVDS). Секреты — только в `/opt/stirki/.env` на сервере.

**Обновление** (код берётся из GitHub, на сервере код не править — только `.env`):

```bash
ssh stirki
cd /opt/stirki && git pull && ./run.sh dev       # пока идут тесты; перед запуском клиентов — ./run.sh prod
```

**ISPmanager отключён.** Хостер предустановил панель, её nginx занимал порт 80. Службы панели
(nginx, apache2, mysql, named, exim4, dovecot, proftpd, php-fpm, ihttpd) остановлены и убраны
из автозапуска, cron-задачи панели закомментированы (копия — `/root/crontab.before-disable-ispmanager.bak`).
Без этого панель сама поднимает nginx обратно. Вернуть: `crontab /root/crontab.before-disable-ispmanager.bak`
и `systemctl enable --now <служба>` — но тогда Caddy не сможет занять порты 80/443.

> ⚠️ Так отключить панель не получилось (проверено 2026-11-13): процесс `core ispmgr` остался запущен,
> заново дописал свои задачи в crontab и поднял службы обратно — из интернета снова открыты FTP, почта,
> DNS и сама панель (:1500). Панель нужно отключить в личном кабинете FirstVDS (TODO, «Деплой»).

**Первичная установка на чистый сервер:**

```bash
apt-get install -y git && curl -fsSL https://get.docker.com | sh
git clone https://github.com/Lightthouse/stirki.git /opt/stirki && cd /opt/stirki
cp .env.example .env && chmod 600 .env && nano .env   # DOMAIN=stirkaon.com, пароли (openssl rand -hex 32), ключи
./run.sh prod
```

> Если контейнер Caddy при первом запуске упал на занятом порту, после освобождения порта его
> нужно пересоздать (`docker compose --profile prod up -d --force-recreate --no-deps caddy`),
> иначе он остаётся без сети и не может получить сертификат.

Caddy сам получит HTTPS-сертификаты (на домен и на `www.`, который редиректит на основной). Проверка: `curl https://stirkaon.com/api/health`.

```bash
docker compose --profile prod ps                 # статус
docker compose --profile prod logs -f backend    # логи бэкенда
git pull && ./run.sh prod                        # обновление
docker exec -it stirki-db psql -U stirki -d stirki
```

Postgres и Adminer слушают только `127.0.0.1` сервера — из интернета они недоступны.
Открыть их со своего компьютера — через SSH-туннель:

```bash
ssh -L 8081:localhost:8081 stirki
# затем в браузере: http://localhost:8081 (Adminer)
```

**Резервные копии БД.** `./run.sh backup` пишет сжатый `pg_dump` в `/var/backups/stirki` (вне репозитория:
он публичный) и оставляет 14 последних копий — сейчас это килобайты. На сервере запускается по cron в 04:00:

```bash
0 4 * * * cd /opt/stirki && ./run.sh backup >> /var/log/stirki-backup.log 2>&1
```

Восстановление: `gunzip -c /var/backups/stirki/<файл>.sql.gz | docker exec -i stirki-db psql -U stirki -d stirki`
(в пустую БД). Копии лежат на том же сервере — от потери сервера не спасают. Рекламные картинки из
`advertising/` в бэкап не входят (решение 2026-11-13): при потере их загружают в админке заново.

**Логи Docker** ограничены в `/etc/docker/daemon.json` (`max-size: 10m`, `max-file: 3` на контейнер) —
без этого json-логи контейнеров растут бесконечно. Действует на контейнеры, созданные после рестарта Docker.

## 4. Эксплуатация

### Админка (`/admin`)

Заказы (смена статуса, комментарий, статус оплаты), клиенты, прайс услуг, системные настройки,
реклама (загрузка картинок), история статусов, статистика рекламы и посещений сайта. Время показывается по МСК.

Отмена заказа и возврат денег — вручную (решение 2026-11-13): клиент пишет в поддержку, администратор ставит
статус «Отменено» в админке и делает возврат в интернет-банке Точки. Сам клиент заказ отменить не может.

Инструкция для сотрудников встроена в админку: открывается на главной странице и в пункте меню
«Инструкция». Текст — `src/admin_templates/_help_content.html`; при изменении логики работы
с заказами, статусами или настройками обновлять и его.

### Реклама

Картинками управляют в админке, раздел «Реклама», без перезапуска: загрузить (jpg, jpeg, png, webp, gif,
до 5 МБ), включить/выключить галочкой «Показывать», удалить. Сайт показывает только включённые
(`GET /api/advertising` читает таблицу `ads`). Код — `src/services/ads.py`, раздел админки — `AdAdmin`.

- Файлы лежат в `advertising/`. В Docker папка подключена томом (`compose.yml`, `./advertising:/app/advertising`),
  в образ не копируется — загруженное переживает пересборку. Загруженные через админку файлы в git не попадают,
  но лежат в папке репозитория на сервере: при переносе сервера копировать `advertising/` вместе с дампом БД.
- К имени загруженного файла добавляется случайный префикс (`a3f9-сплетницы.jpg`). Статистика просмотров
  (`ad_views`, вид `ad_view_stats`) считается по пути файла, поэтому новая картинка с тем же именем не смешается
  со старой. Картинку не заменяют, а загружают новую и выключают старую.
- Удаление стирает файл и строку `ads`, но не статистику: в «Статистике рекламы» она остаётся с пометкой «удалена».
  Чтобы сохранить название в статистике, картинку лучше выключать, а не удалять.
- Показ — `frontend/src/components/AdViewer.tsx`. Картинки начинают грузиться в фоне сразу при открытии
  страницы заказа (`OrderPage`, если бесплатный тариф включён), пока клиент выбирает адрес и тариф. Отсчёт по каждой начинается только
  после её загрузки (пока грузится — «загрузка…»), время считается по часам, а не по тикам таймера. Не загрузилась
  за 15 с — показ идёт дальше, просмотр в `ad_views` не пишется. Чем легче файл, тем меньше ожидание: лучше jpg до 500 КБ.
- Начальные картинки (`сплетницы.jpg`, `счастливыечасы.jpg`) лежат в git и заносятся в `ads` в `pg_init/01-schema.sql`.
