# Стирка ON

![stirki](./stirki_bot_logo.jpg)

Гиперлокальный сервис доставки стирки в Мытищах: https://stirkaon.com.
Клиент находит сервис по QR-коду на листовке, оформляет заказ в PWA, пеший курьер
забирает бельё у двери, мы стираем, сушим, гладим и возвращаем.

Открытые задачи — в [`docs/TODO.md`](docs/TODO.md). Текст оферты — [`docs/оферта.txt`](docs/оферта.txt)
(на сайте показывается из `frontend/src/components/ui/OfferModal.tsx`, при правках менять оба).

## 1. Как сервис работает для клиента

```
QR на листовке → stirkaon.com → лендинг → /login (телефон + SMS) → /order (карточки)
    → корзина → заказ → [бесплатно: сразу в работу | платно: оплата в Точке]
    → /order/:id — статус заказа → доставлено
```

1. **QR-код.** Листовки ведут на главную без параметров, поэтому отличить переход с листовки (и с какого дома)
   от другого захода нельзя — считаются все заходы неавторизованных посетителей на главную. Заход пишется в
   `landing_visits` не чаще раза за сессию вкладки; браузер получает случайный `visitor_id` (localStorage),
   по нему считаются уникальные посетители. В админке «Посещения сайта» — по дням (МСК): всего заходов и уникальных.
2. **Вход и регистрация.** Клиент вводит номер → 4-значный код по SMS (SmsAero, TTL 5 мин, повтор не чаще
   раза в 58 с, 5 неверных вводов сжигают код). Токен живёт 60 дней и продлевается.
   - **Зарегистрированный номер** (`Client.is_registered`: номер подтверждён и есть согласие с офертой) —
     код уходит сразу, вводится только код. Согласие на рассылку при входе не меняется.
   - **Новый номер** — `request-code` без согласия с офертой код не шлёт и клиента не создаёт, а отвечает
     `registration_required`. Фронтенд показывает шаг «Регистрация»: две галочки (требование SMS-сервиса):
     «принимаю оферту и политику» — обязательна, без неё код не отправляется; «согласен на рекламные СМС» — по желанию,
     изначально пустая. Время согласий (`clients.offer_accepted_at` / `sms_marketing_consent_at`, null — согласия нет)
     пишется только после подтверждения кода. Затем — имя. В админке — колонка «Согласие на рассылку».
   - Email при регистрации не спрашивается (с 2026-11-20) — он нужен только для кассового чека и вводится в корзине
     платного заказа (см. «Оплата»).
   - Ответ `request-code` показывает, зарегистрирован ли номер, — это осознанно (без этого не разделить вход и регистрацию).
3. **Заказ** — вертикальные карточки:
   - **Адрес** — только выбор из списка (зона обслуживания в `src/addresses.py`), подъезд, этаж, квартира, комментарий. Адрес прошлого заказа подставляется.
   - **Тариф** — бесплатный или платный (см. ниже).
   - **Машинка** (только бесплатный тариф) — витрина: состояния случайные, реального парка за ней нет.
   - **Что стираем** — пакет или вещь, допуслуги, на бесплатном тарифе — просмотр рекламы (картинки, включённые в админке «Реклама», каждый показ пишется в `ad_views`).
   - **Оформление** — по кнопке «Оформить заказ» (после проверки адреса, передачи и email) показывается окно
     «Мы не стираем» (обувь, верхняя одежда, домашний текстиль, ковры); заказ создаётся только по «Хорошо», клик мимо
     окна — отмена. Текст — в `OrderPage.tsx`; если список поменяется — сверить с «О сервисе» и офертой.
4. **Оплата** (платный тариф). В корзине под «Как передать вещи» — обязательное поле «Email для чеков»: подставлен
   email с прошлого заказа (`clients.email`), клиент может его поменять, при оформлении он сохраняется в профиль.
   Бесплатный заказ email не требует. Если фронтенд email не прислал (старая версия из кэша браузера), берётся
   сохранённый; нет и его — ошибка «Укажите email для чека». Заказ создаётся в статусе «Ожидает оплаты», клиент уходит на платёжную
   ссылку Точки (СБП или карта, ссылка живёт 1 час; T-Pay убран 2026-11-20). Статус оплаты сервер сверяет с Точкой сам:
   при возврате клиента, при открытии заказа и фоновой задачей раз в минуту. Оплачен → «В пути»;
   отклонён или ссылка истекла → «Отменено».
   Если Точка не выдала ссылку (ошибка API, неверная настройка), заказ сразу отменяется
   (`changed_by=system`), клиент видит окно «Оплата не прошла» с контактами поддержки, операторам уходит
   письмо «Сбой оплаты» с ответом Точки. Такой заказ (платный, отменён, без `operation_id`) скрыт из
   истории клиента, в админке остаётся.
   Ссылка создаётся методом `payments_with_receipt` — с кассовым чеком по 54-ФЗ, который Точка шлёт на
   email клиента. Позиции чека — пакеты и вещи (`PricingService.order_lines`): количество = число
   пакетов/вещей, цена за единицу уже включает допуслуги, они же перечислены в названии позиции.
   В конце названия — номер заказа («Стирка одной вещи (глажка), заказ ST-123»): названия позиций
   печатаются в чеке всегда, поэтому чек с почты клиента однозначно находится в админке.
   Без НДС (`vatType: none`), предмет расчёта — услуга, полный расчёт. Бесплатные заказы чека не имеют.
   Документация API Точки — локально в `docs/tochka/` (в git не хранится: 2,8 МБ, и GitHub принимает ссылки на
   публичные ключи Точки в ней за секреты). Скачать: https://developers.tochka.com/llms-full.txt,
   https://developers.tochka.com/llms.txt, https://enter.tochka.com/doc/openapi/swagger.json.
   `swagger.json` главнее текста `llms-full.txt`.

   **Номера заказа и платежа.** Номер заказа — `ST-<orders.id>` (`Order.number`), одинаковый на сайте,
   в письмах операторам и в админке. У платежа в Точке три идентификатора, все хранятся в `orders`:
   - `payment_link_id` — `paymentLinkId`, номер заказа для Точки: `ST-123-K7Q2`. Его видит клиент на
     странице оплаты, по нему оператор ищет заказ в админке (поиск в «Заказах») по реестру Точки.
     Случайный хвост нужен, потому что Точка не принимает повторный `paymentLinkId`, а `orders.id`
     повторяется: локальная разработка ходит в ту же Точку, а БД пересоздаётся с нумерацией с 1.
   - `operation_id` — ID операции, его выдаёт Точка; по нему сервер сверяет статус оплаты.
   - `payment_token` — секретный UUID в адресе возврата после оплаты (`/?payment_token=…`), клиенту
     как номер не показывается.
5. **Статус заказа** — таймлайн, поллинг раз в 60 с, кнопка «Связаться с поддержкой».
   Контакты поддержки (телефон, Telegram, email) хранятся в `system_settings`, меняются в админке и
   показываются компонентом `SupportContacts`: в окне поддержки, в «О сервисе» (доступно и до заказа)
   и в окне ошибки оплаты. Пустой контакт не показывается.
6. **Операторы** получают письмо о каждом новом заказе (бесплатный — сразу, платный — после оплаты)
   и двигают статусы вручную в админке `/admin`.

### Тарифы и правила

| | Бесплатный | Платный |
|---|---|---|
| Цена | 0 ₽ | по прайсу из БД |
| Условие | просмотр рекламы | оплата через Точка Банк |
| Что стираем | только пакет до 3 кг | пакеты и вещи |
| Лимит позиций | 1 пакет | 5 пакетов + 1 вещь |
| Допуслуги | нет | глажка, кондиционер, вакуумный пакет |
| Ограничение | 1 бесплатный заказ в сутки (МСК) на адрес | — |

- **Цена** = (база + допуслуги за пакет) × пакеты + (цена вещи + допуслуги за вещь) × вещи.
  Допуслуги выбираются на весь заказ и применяются к каждой позиции. Прайс — таблица `services`, цены — как в оферте
  (пакет 990 ₽, вещь 190 ₽, глажка +190 ₽ за вещь / +990 ₽ за пакет, кондиционер +100 ₽, вакуумный пакет +150 ₽).
  Если у допуслуги цена за пакет другая, она задаётся отдельной услугой со slug `<допуслуга>_bag` (сейчас только
  `ironing_bag` — «Глажка пакета»); такая услуга не выбирается сама и не показывается клиенту отдельной строкой.
- **Приём заказов** — ежедневно 9:00–21:00 МСК (курьеры работают 7:00–21:00). Вне часов сервер отклоняет заказ, клиенту показывается модалка.
- **Вечерние заказы** — оформленные с 19:00 МСК (`next_day_delivery_from_hour`) курьер забирает сразу, а возвращает
  на следующий день; нужное время клиент пишет в комментарии. Флаг фиксируется в заказе при создании
  (`orders.next_day_delivery`) и виден клиенту на экране заказа, операторам — в письме и в админке. Корзина
  предупреждает об этом по московскому времени устройства клиента. Условие продублировано в оферте (п. 4.7.1).
- **Передача вещей** — в корзине клиент обязательно выбирает «Забрать и оставить у двери» или «Лично в руки»
  (`orders.handover`: `door` / `hand`, `src/enums.py` → `Handover`). Без выбора заказ не оформляется (на сервере
  поле обязательное). Выбор виден клиенту на экране заказа и в истории рядом с комментарием, операторам — в письме
  и в админке; там же его можно поменять, если клиент попросил по телефону.
  Расхождение с офертой: в ней описана только передача у двери (п. 4.4, 4.8 — «при отсутствии Заказчика
  курьер оставляет вещи у двери с фотофиксацией»), вариант «лично в руки» не упомянут. Оферту решено
  выравнивать по завершении проекта.
- **Срок выполнения** — на лендинге и экране заказа обещано 4 часа (обычный срок), в оферте (п. 4.7) — 4–8 часов
  с запасом на высокую загрузку. Расхождение намеренное, выравнивать не нужно.
- **Один активный заказ** на клиента. Неоплаченный заказ не считается активным.
- Лимиты, часы приёма, час перехода на доставку завтра, лимит бесплатных заказов на адрес, число и длительность рекламы, доступность бесплатного тарифа, контакты поддержки, получатели писем о заказах — меняются в админке («Системные настройки»), без деплоя.

### Статусы заказа

`waiting_payment` (Ожидает оплаты) → `courier_pickup` (В пути) → `picked_up` (Забрали) → `washing` (Чистим)
→ `courier_delivery` (Идём отдавать) → `delivered` (Доставлено); в любой момент — `canceled` (Отменено).
Каждая смена пишется в `order_status_history` с отметкой, кто изменил (`system`, `admin`, `tochka`).

## 2. Устройство проекта

```
src/          бэкенд: FastAPI, async SQLAlchemy, sqladmin
frontend/     PWA: React 19 + TypeScript + Vite + vite-plugin-pwa
pg_init/      SQL-схема БД и сид-данные (единственный источник правды по таблицам)
advertising/  файлы рекламных картинок (раздаются бэкендом как /advertising/*; в Docker — том)
restyle/      HTML-макеты дизайна (референс, в сборку не входят)
http_requests/ запросы для HTTP-клиента IDE (SmsAero, Точка)
```

### Бэкенд

Слои, зависимости только вниз:

```
src/api/routers/   эндпоинты, валидация, HTTP-ошибки
src/services/      бизнес-логика и интеграции
src/repositories/  запросы к БД, коммиты
src/models/        ORM-модели
```

- `src/schemas/` — Pydantic-модели запросов/ответов, `src/enums.py` — статусы заказа и оплаты, `src/settings.py` — настройки из `.env` (по классу на подсистему).
- Сервисы: `pricing.py` (цена), `payment.py` (Точка Банк), `payment_sync.py` (сверка оплат + фоновая задача), `notifications.py` (email операторам), `schedule.py` (часы приёма, МСК), `sms.py` (SmsAero), `auth.py` (генерация кода).
- Авторизация: Bearer-токен (UUID в `clients.auth_token`), зависимость `get_current_client` в `src/api/dependencies.py`.
- Создание заказа сериализуется `pg_advisory_xact_lock(client_id)`, чтобы не получить два активных заказа.
- Некритичная интеграция (email операторам) не роняет основной сценарий: ошибки только логируются.
- Админка — `src/admin.py` (sqladmin), вход по `ADMIN_USERNAME` / `ADMIN_PASSWORD`.

### Фронтенд

Только React + react-router: без state-менеджера и UI-кита.

- Страницы в `frontend/src/pages/`: `LandingPage` (`/`), `LoginPage` (`/login`), `OrderPage` (`/order`), `OrderStatusPage` (`/order/:id`).
- `OrderPage` владеет всем состоянием, карточки (`components/swipe/`) — презентационные.
- API — только через `api/client.ts` (fetch, Bearer, таймаут 15 с) и `api/index.ts`. Типы зеркалят схемы бэкенда — `types/index.ts`.
- Стили — один `index.css`, иконки — Font Awesome.

### База данных

PostgreSQL 16. Схема и начальные данные (статусы, прайс, настройки) — `pg_init/01-schema.sql`,
единственный источник правды. Файл выполняется **только при первом создании тома** Postgres. Миграций нет:
реальных клиентов пока нет, поэтому после правки `01-schema.sql` БД пересоздаётся. Все данные (клиенты, заказы,
правки в админке) при этом удаляются.

```bash
docker compose --profile prod down        # остановить контейнеры (тома остаются)
docker volume rm stirki_pg_data           # удалить БД
./run.sh local                            # или ./run.sh server на сервере — БД создастся из pg_init
```

> Когда появятся реальные клиенты, пересоздавать БД будет нельзя — тогда понадобятся миграции.

Основные таблицы: `clients`, `orders`, `order_statuses`, `order_status_history`, `services`,
`system_settings` (одна строка с рантайм-настройками), `landing_visits` (+ представление `landing_visit_stats`), `ad_views`,
`sms_sends` (отправленные SMS-коды для лимитов по IP).

### Соглашения

- Язык проекта — русский: тексты для пользователя, комментарии, коммиты, документация. Имена в коде и slug'и — английские.
- Статусы, услуги и улицы между слоями передаются латинскими slug'ами, кириллица — только для отображения.
- Комментарии объясняют «почему», а не «что».
- Линтер: `uv run ruff check src/`.

## 3. Запуск

### Переменные окружения

```bash
cp .env.example .env
```

| Переменные | Зачем |
|---|---|
| `DB_USER`, `DB_PASSWORD`, `DB_PORT` | PostgreSQL |
| `DOMAIN` | домен для Caddy (HTTPS), CORS и адреса возврата после оплаты |
| `SECRET_KEY`, `ADMIN_USERNAME`, `ADMIN_PASSWORD` | сессии и вход в админку; без своих `SECRET_KEY` и `ADMIN_PASSWORD` бэкенд не запускается (и локально тоже) |
| `SMSAERO_EMAIL`, `SMSAERO_API_KEY` | SMS с кодом входа. Сама отправка включается флагом в админке, не переменной |
| `SMSAERO_SIGN` | имя отправителя, одобренное в кабинете SmsAero; пусто — тестовое «Sms Aero». Неодобренное имя ломает отправку |
| `TOCHKA_TOKEN`, `TOCHKA_CUSTOMER_CODE_BUISNESS` | эквайринг Точка Банк |
| `TOCHKA_MERCHANT_ID` | торговая точка эквайринга (`merchantId` из `GET /acquiring/v1.0/retailers`). У компании две точки — stirkaon.ru и stirkaon.com (`200000000048338`); при нескольких точках без этого поля Точка отвечает 400 «Field merchantId is required» |
| `TOCHKA_TAX_SYSTEM_CODE` | необязательно: система налогообложения для чека (`usn_income`, `patent`, …); пусто — не передаётся |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD` | ящик-отправитель писем операторам о новых заказах и сбоях оплаты. Ящик на Яндексе: `SMTP_HOST=smtp.yandex.ru`, `SMTP_PORT=465`, пароль — «пароль приложения» Яндекса (обычный не подойдёт; сервер другой почты, например `smtp.mail.ru`, его отвергнет). **Получатели** — не здесь, а в админке: «Системные настройки» → «Уведомления о заказах: email» (`system_settings.notify_emails`, адреса через запятую; до 2026-11-20 были в `NOTIFY_EMAIL`). Названия допуслуг в письме — из таблицы `services`, у платного заказа есть «Платёж в Точке» (`payment_link_id`). Не настроен SMTP или пуст список получателей — письма не отправляются, в логе предупреждение. Лимит Яндекса — 300 писем в сутки через SMTP, каждый получатель считается отдельным письмом (справка Яндекса «Отправить много писем», 2026-11-20) |

> Окружение одно — и локально, и на сервере (`APP_ENV` и режимы dev/prod убраны 2026-11-18). Оплата через Точку
> настоящая везде: платный заказ создаёт реальную ссылку. Вход по SMS включается флагом «Вход по SMS» в админке
> («Системные настройки»); пока он выключен, код показывается прямо на странице входа и войти можно под любым
> номером — по концепции приложения это безопасно (клиент видит только свои заказы).

### Режимы `run.sh`

| Команда | Что запускается |
|---|---|
| `./run.sh local` | Postgres и Adminer в Docker; бэкенд (uvicorn `--reload`, :8001) и фронтенд (Vite, http://localhost:5173) на хосте — для разработки |
| `./run.sh server` | весь стек в Docker (бэкенд, сборка фронтенда, Caddy) — так запускается сервер |
| `./run.sh stop` | остановить всё |

Пока в админке выключен «Вход по SMS» (по умолчанию), код входа показывается прямо под полем ввода. Админка — http://localhost:5173/admin,
Adminer — http://localhost:8081.

### Сервер

Рабочий сервер: FirstVDS, Ubuntu 24.04, `ssh stirki` (root), проект в `/opt/stirki`, домен
stirkaon.com → 195.140.146.185 (DNS у FirstVDS). Секреты — только в `/opt/stirki/.env` на сервере.

**Первичная установка на чистый сервер:**

```bash
apt-get install -y git && curl -fsSL https://get.docker.com | sh
git clone https://github.com/Lightthouse/stirki.git /opt/stirki && cd /opt/stirki
cp .env.example .env && chmod 600 .env && nano .env   # DOMAIN=stirkaon.com, пароли (openssl rand -hex 32), ключи
./run.sh server
```

> Если контейнер Caddy при первом запуске упал на занятом порту, после освобождения порта его
> нужно пересоздать (`docker compose --profile prod up -d --force-recreate --no-deps caddy`),
> иначе он остаётся без сети и не может получить сертификат.

Caddy сам получит HTTPS-сертификаты (на домен и на `www.`, который редиректит на основной). Проверка: `curl https://stirkaon.com/api/health`.
Caddy включает HTTP/3 и объявляет его браузерам заголовком `Alt-Svc`, поэтому в `compose.yml` открыт и `443/udp`.
Без него Safari периодически не получает ответ и показывает «Load failed» (так было 2026-11-18 при входе админа).

```bash
docker compose --profile prod ps                 # статус
docker compose --profile prod logs -f backend    # логи бэкенда
git pull && ./run.sh server                      # обновление
docker exec -it stirki-db psql -U stirki -d stirki
```

Postgres и Adminer слушают только `127.0.0.1` сервера — из интернета они недоступны.
Открыть их со своего компьютера — через SSH-туннель:

```bash
ssh -L 8081:localhost:8081 stirki
# затем в браузере: http://localhost:8081 (Adminer)
```

**Резервные копии БД.** `./run.sh backup` пишет сжатый `pg_dump` в `/var/backups/stirki` (вне репозитория:
он публичный) и оставляет 14 последних копий — сейчас это килобайты. На сервере запускается в 04:00 из
`/etc/cron.d/stirki-backup` (не из crontab root: его переписывает ISPmanager), лог — `/var/log/stirki-backup.log`:

```bash
0 4 * * * root cd /opt/stirki && ./run.sh backup >> /var/log/stirki-backup.log 2>&1
```

Восстановление: `gunzip -c /var/backups/stirki/<файл>.sql.gz | docker exec -i stirki-db psql -U stirki -d stirki`
(в пустую БД). Копии лежат на том же сервере — от потери сервера не спасают. Рекламные картинки из
`advertising/` в бэкап не входят (решение 2026-11-13): при потере их загружают в админке заново.

**Логи Docker** ограничены в `/etc/docker/daemon.json` (`max-size: 10m`, `max-file: 3` на контейнер) —
без этого json-логи контейнеров растут бесконечно. Действует на контейнеры, созданные после рестарта Docker.

## 4. Эксплуатация

### Админка (`/admin`)

Заказы (смена статуса, комментарий, статус оплаты), клиенты, прайс услуг, системные настройки,
реклама (загрузка картинок), история статусов, статистика рекламы и посещений сайта. Время показывается по МСК.

Интерфейс sqladmin переведён на русский: у sqladmin нет i18n, поэтому `src/admin_templates/sqladmin/base.html`
наследует оригинальный шаблон (подключён в `create_admin` под префиксом `original/`) и скриптом заменяет английские
надписи — данные в ячейках таблиц не трогает. Сообщения форм — встроенная русская локаль WTForms (`RussianForm`).
Статусы оплаты, тип стирки и «Кем» в истории показываются по-русски, хранятся латинскими slug'ами.
После обновления sqladmin — проверить, не появились ли новые английские надписи.

Списки (`src/admin.py`, общий класс `BaseAdmin`): 50 строк на странице; фильтры в боковой панели — у заказов статус,
дата (сегодня, вчера, 7/30 дней, этот месяц по МСК), тариф, оплата, передача, доставка завтра, у клиентов — дата
регистрации, согласие на рассылку, верификация (`ChoiceFilter` — подписи по-русски вместо встроенных «All/Yes/No»).
Сортировка по клику на заголовок; по статусу — в порядке жизни заказа (`OrderAdmin.sort_query`).
Кнопка «Столбцы» (`src/admin_templates/list.html`) скрывает столбцы; выбор хранится в localStorage браузера
сотрудника отдельно для каждого раздела.

Отмена заказа и возврат денег — вручную (решение 2026-11-13): клиент пишет в поддержку, администратор ставит
статус «Отменено» в админке и делает возврат в интернет-банке Точки. Сам клиент заказ отменить не может.

Инструкция для сотрудников встроена в админку: открывается на главной странице и в пункте меню
«Инструкция». Текст — `src/admin_templates/_help_content.html`; при изменении логики работы
с заказами, статусами или настройками обновлять и его.

### SMS (SmsAero)

Документация API: https://smsaero.ru/integration/documentation/api/ (одна страница, версия 7.0; изучена 2026-11-18).

**Как устроено.** `POST /api/auth/request-code` (`src/api/routers/auth.py` → `src/services/sms.py`, библиотека
`smsaero-api-async`). Отправка включается флагом `system_settings.sms_enabled` («Вход по SMS» в админке):
- выключен (по умолчанию) — SMS не шлётся, код возвращается в ответе API и показывается на странице входа;
- включён — код уходит по SMS; в лог пишутся id сообщения, статус, подпись и стоимость
  (`SMS отправлено: id=…`); id ищется в кабинете SmsAero.
- **Отладочные номера** — в админке («Системные настройки»): флаг «Отладочные номера включены»
  (`system_settings.debug_phones_enabled`, по умолчанию выключен) и список через запятую (`debug_phones`, по умолчанию
  `+7 999 999-99-99, +7 888 888-88-88`). При включённом флаге номера из списка получают код на странице, SMS на них
  не шлётся, даже когда вход по SMS включён; в лог пишется предупреждение `Код для отладочного номера …`. Флаг выключен —
  список не действует. Номер сравнивается по цифрам, ведущая 8 = 7 (`is_debug_phone` в `src/services/auth.py`).
- **Лимиты по IP** (`src/services/sms_limits.py`): «раз в 58 с на номер» не мешает перебирать разные номера, а каждая
  SMS платная. Поэтому настоящие отправки (не отладочные номера, вход по SMS включён) считаются и по IP: по умолчанию
  не больше 5 за 10 минут, 15 за сутки и 50 за неделю. Значения — в админке («Системные настройки», «SMS с одного IP»),
  действуют сразу. Отправки хранятся в таблице `sms_sends` 30 дней (раздел админки «Отправленные SMS» — видно, с каких
  IP и на какие номера), неудачные попытки тоже считаются. Отказ — HTTP 429 с текстом «попробуйте через …» и запись
  `Лимит SMS-кодов для IP …` в логе. Общий потолок расходов — в кабинете SmsAero.
  IP клиента бэкенд берёт из `X-Forwarded-For` от Caddy (`--proxy-headers --forwarded-allow-ips *` в `Dockerfile.backend`;
  безопасно, потому что порт бэкенда открыт только на 127.0.0.1). Без этого все клиенты выглядели бы одним IP Caddy.
- Номер проверяется на сервере: 11 цифр, мобильный `79…` (или отладочный из включённого списка) — неполный номер
  SmsAero не примет.
- Текст: «Код для входа в Стирка ON: 1234. stirkaon.com» (`CODE_TEXT`) — до 70 символов, т.е. одна SMS,
  с источником, как требует бесплатная подпись.
- Проверить отправку без денег: библиотечный `enable_test_mode()` шлёт в `sms/testsend` (ответ как у боевого,
  ничего не отправляется и не списывается) — так проверено 2026-11-18.

Через аккаунт ещё не отправлено ни одного настоящего SMS (история `sms/list` пуста на 2026-11-18).

**API, главное:**
- Шлюз `https://gate.smsaero.ru/v2/` (библиотека сама переключается на резервные `gate.smsaero.org`,
  `gate.smsaero.net`). Авторизация — HTTP Basic: email аккаунта + API-ключ. Проверка ключа — `GET auth`.
- Ответ всегда `{"success": bool, "data": ..., "message": ...}`; ошибки — HTTP 400 (неверный параметр, в т.ч.
  номер), 402 (нет денег), 404 `Invalid ip-address` (если в кабинете включён белый список IP).
- Отправка: `sms/send` — `number` (`79991234567`, 11 цифр без `+`), `sign`, `text`; необязательно `callbackUrl`
  (POST со статусом, ждёт HTTP 200, повторяет до 24 ч), `dateSend`. В ответе `data[0].id` — для `sms/status?id=`.
- Статусы: 0 очередь, 1 доставлено, 2 не доставлено, 3 передано оператору, 4 ожидание статуса,
  6 отклонено, **8 на модерации**.
- Тестовый режим: `sms/testsend` / `sms/teststatus` — ничего не отправляет и не списывает, ответ как у боевого
  (в библиотеке — `enable_test_mode()`). Тестовый ключ — в кабинете «Настройки → API и SMPP».
- Ошибки текста, на которые легко наступить: смешение кириллицы и латиницы в одном слове
  («symbols from cyrillic and latin are used in word») и повтор на тот же номер («multi send on numbers»,
  лимит настраивается в кабинете).

**Подпись (имя отправителя) и модерация:**
- Своих подписей в аккаунте нет (`sign/list` пуст на 2026-11-18). Подпись по умолчанию `SMS Aero` по документации —
  только для тестов. Без своей подписи сообщения идут по каналу «бесплатная подпись» (FREE SIGN), и тогда
  в тексте обязательно указывать источник (название, сайт) — иначе операторы могут блокировать.
- Модерация: «все SMS проходят ручную модерацию до 5–10 минут; чтобы отключить — заключите договор» (раздел
  «Реквизиты и договоры» в кабинете). Договор заключён; снята ли модерация — станет видно по первой реальной
  отправке (статус 8 = на модерации).
- Подпись берётся из `SMSAERO_SIGN`; пусто — библиотечная `Sms Aero` (так сейчас). После одобрения своей подписи
  в кабинете — вписать её в `.env`.

**Цены за SMS, ₽** (`GET tariffs`, 2026-11-18; МегаФон / МТС / билайн / t2):
FREE SIGN 14,19 / 9,89 / 46,29 / 9,79; PAY SIGN (своя подпись) 38,60 / 8,69 / 12,59 / 8,28;
AUTH 8,30 / 8,49 / 11,19 / 12,59. Канал AUTH дешевле, но как на него попасть, в документации не сказано —
спросить поддержку SmsAero (вероятно, нужна подпись, зарегистрированная под авторизацию).

**Альтернативные каналы для кодов** (не используются):
- `telegram/send` (`number`, `code`; при недоставке в Telegram шлёт SMS с `text` и `sign`).
- Мобильная авторизация `mobile-id/send` → `verify` / `status`: оператор подтверждает номер через SIM-PUSH,
  иначе шлёт SMS-код; сессия 180 с, подпись должна быть одобрена в кабинете («Подписи → Mobile ID»).
  Тестовым ключом код всегда `1234`.
- Flash call / звонок-сброс в API не описаны.

### Реклама

Картинками управляют в админке, раздел «Реклама», без перезапуска: загрузить (jpg, jpeg, png, webp, gif,
до 5 МБ), включить/выключить галочкой «Показывать», удалить. Сайт показывает только включённые
(`GET /api/advertising` читает таблицу `ads`). Код — `src/services/ads.py`, раздел админки — `AdAdmin`.

- Файлы лежат в `advertising/`. В Docker папка подключена томом (`compose.yml`, `./advertising:/app/advertising`),
  в образ не копируется — загруженное переживает пересборку. Загруженные через админку файлы в git не попадают,
  но лежат в папке репозитория на сервере: при переносе сервера копировать `advertising/` вместе с дампом БД.
- К имени загруженного файла добавляется случайный префикс (`a3f9-сплетницы.jpg`). Статистика просмотров
  (`ad_views`, вид `ad_view_stats`) считается по пути файла, поэтому новая картинка с тем же именем не смешается
  со старой. Картинку не заменяют, а загружают новую и выключают старую.
- Удаление стирает файл и строку `ads`, но не статистику: в «Статистике рекламы» она остаётся с пометкой «удалена».
  Чтобы сохранить название в статистике, картинку лучше выключать, а не удалять.
- Показ — `frontend/src/components/AdViewer.tsx`. Картинки начинают грузиться в фоне сразу при открытии
  страницы заказа (`OrderPage`, если бесплатный тариф включён), пока клиент выбирает адрес и тариф. Отсчёт по каждой начинается только
  после её загрузки (пока грузится — «загрузка…»), время считается по часам, а не по тикам таймера. Не загрузилась
  за 15 с — показ идёт дальше, просмотр в `ad_views` не пишется. Чем легче файл, тем меньше ожидание: лучше jpg до 500 КБ.
- Начальные картинки (`сплетницы.jpg`, `счастливыечасы.jpg`) лежат в git и заносятся в `ads` в `pg_init/01-schema.sql`.
